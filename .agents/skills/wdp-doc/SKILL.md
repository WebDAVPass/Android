# WebDAVPass 文档

<a id="summary"></a>

## 摘要

WebDAVPass 文档标准：让每一页都可检索、新人可读，并且精确到足以让 agent 与维护者使用。先执行仓库 `AGENTS.md` 与已落地的门禁，再用本工作流处理渐进细节、语料库审计与词数预算。每个事实只有一个所有者：源码、测试、文档、Agent Note 各自持有自己那类真相。

<a id="workflow"></a>

## 工作流

对每个请求的范围按此顺序执行。让常见读者路径保持简短，但不要仅为减少字数而删掉失败、归属、限制或其他必需的契约。

1. 读取根目录与更具体的 `AGENTS.md`、[文档标准](../../../Docs/AGENTS.md)、目标页、其源码与测试。
2. 按主要职责与读者给页面分类：产品快速上手、用户任务指南、贡献者教程、架构概览、参考页、agent 指令或决策记录。
3. 把页面放到最近的所有者处；`Docs/` 用于跨模块的学习、用户、开发者、架构与会过期的材料。
4. 写细节之前先界定读者的起点状态、可观察结果、可能的失败、恢复路径与下一个有用的深度。
5. 按顺序写 H1 标题、`## Summary`、`## Table of Contents`、面向用户的内容、面向开发者的内容、可选的 `## Further Exploration` 与最后的 `## Dev Note`。
6. 对照源码、测试或当前决策所有者校验每条断言，并按下方事实核查流程实际运行页面所指示的操作。先更新所有者，再改任何派生产物。
7. 先跑聚焦检查，再跑 `npm run test:docs` 与 `git diff --check`；完整复读 diff，先查正确性，再查简洁度与仓库契合度。

<a id="fact-check-procedure-test-do-not-assume"></a>

## 事实核查流程：实测，不要假定

文档陈述产品今天的行为；操作类断言的唯一可采信证据是实际运行过。每份新文档、以及每个声称操作、命令、默认值、错误或平台差异的新段落，都必须走本流程。

1. **写使用指引前先判定对象形态。** 读事实，绝不看名字：动作是 Gradle 任务、npm 脚本还是应用内入口，作用于哪个模块；权限、组件、资源各自的所有者在哪。绝不为不存在的形态写指引。
2. **在当前检出上实际运行每个声称的操作。** 逐条执行文档将要展示的命令、配置片段或操作步骤；只记录你观察到的内容，包括确切输出、告警与失败形态。若某条断言依赖你没有的密钥库、设备或网络，说明这一点并点明验证所有者，而不是断言其行为。
3. **删掉无法复现的内容。** 绝不凭记忆、类比或相邻文档搬运命令、字段、默认值或行为。断言无法复现时，改正断言——不是改正测试。
4. **对照最新 master 检查旧文档。** 修订既有页面前先 `git fetch origin`，把该节与 `origin/master` 对比。master 上的过期陈述仍然是错的：按代码改正，而不是按旧散文。

<a id="voice-rules"></a>

## 语气规则

这些规则决定一节可以说什么。它们适用于每一份面向人编写的页面。

- **摘要说明主体能做什么。** 开篇 `Summary` 与面向用户的各节描述用户或 agent 能用该主体做什么——结果、收益、何时选用、主要代价——绝不描述其角色、类型或内部身份。除读者会直接在配置、命令或公共 API 中使用外，省略源码标识符。「该组件注册回调并追加日志」是身份叙述；「你可以为每条消息保存一条笔记，且它在重启后仍在」才是它做的事。
- **开发者各节解释，绝不罗列。** 折叠的实现内容覆盖总体设计概念、架构与粗线条数据流——足以理解该模块如何工作——并链接代码以取精确细节。折叠区内不放完整 API 清单、穷尽列清单、事件载荷枚举或注释复述。
- **Dev Note 是唯一的杂物区。** 半成品想法、草稿、未定方向、实测产物与工作假设只存在于文件末尾的 Dev Note，并明确标注为非权威。其他各节都是打磨过的、描述当前状态的散文。
- **只写当前状态。** 普通文档描述当前代码库。Agent Note 与事故复盘保留各自的历史范围。
- **使用受控技术表达。** 当歧义会改变行为时，让每个句子有明确的主体与一个主动作。每个概念复用一个术语，偏好直接动词，拆开叠加的指令与条件，保留情态与例外。按[页面风格参考页](references/style.md#controlled-technical-expression)中的纪律执行。缩短句子会损失精确性时，不要强行缩短。

<a id="quality-criteria"></a>

## 质量标准

评审时使用这些定义。每节在子节或穷尽细节之前，先用一段简短的定向段落开场。

- **简短：** 常见路径只含其所需的事实；穷尽真相始终只隔一条直接链接或一层细节。
- **直观：** 前置概念先于依赖它的概念，下一个动作显而易见，标题使用读者会搜索的词。
- **友好：** 读者能认出成功、在动手前理解风险、从可能的失败中恢复，并自行决定是否继续深入。
- **准确：** 每条持久断言都有一个所有者，以及与其风险相称的验证路径。
- **agent 可读：** 元数据、稳定标题、锚点、术语、归属与当前或待定状态支持定向检索，无需加载整个语料库。
- **新人可完整重建：** 无仓库背景的职业工程师通过三到五个互链页面即可重建相关架构或特性。

不要对穷尽型参考页施加统一字数上限。衡量入口路径长度、为一次查找而扫过的无关材料、最大一节、标题数与页面大小；检索成本高时按既有领域所有者拆分。

<a id="audit-the-corpus"></a>

## 审计语料库

阅读，不要复述，这些所有者的契约：[Docs/AGENTS.md](../../../Docs/AGENTS.md) 负责层级、教程与参考页形态、分类、预算与 slop 检查清单；[.agents/notes/README.md](../../notes/README.md) 负责 Agent Note 生命周期；根 AGENTS.md 负责常驻指令。审计与编辑都排除 `.agents/notes/archived/`——归档记录是冻结的历史。

对范围内每份面向人的文档（不含 Agent Note）套用标准的写作顺序：定位文档并陈述其自身主题；确定允许的细节层级，把更深的解释连同链接移到拥有它的后代；按预期用途而非路径判定教程或参考页；教程按前置关系与难度排列概念；内容可观的混合形态拆开。移动是原子的，且同一变更里修好所有入站链接。

结构检查之后，用最便宜的探针先追 slop 检查清单：grep 有特点的短语找出重复规则，把手写的清单与状态盘点换成其权威所有者，并从已实现的 Agent Note 中删除迁移计划与将来时的规格话术。用 `npm run verify-doc-budgets --list` 与词数扫描衡量异常值。保留每条承重规则，最好写成一到三行加一条指向其理由的链接；不要只为安置可丢弃的推理而新造一段解释。

<a id="wordcount-budgets"></a>

## 词数预算

`npm run verify-doc-budgets` 把常驻文档与 scripts/doc-budgets.manifest.json 中的上限比较；门禁变红时按 [Docs/AGENTS.md](../../../Docs/AGENTS.md#wordcount-budgets) 中搬迁、压缩、上调的有序策略处理。上限是护栏，不是压缩目标：处于或低于目标时保留至少 5% 余量；只有内容确实需要空间时才上调上限，并在 PR 中说明清单 diff 的理由。

<a id="detailed-references"></a>

## 详细参考页

只加载任务所需的那份参考页。每份参考页都从本文件直接链接，因此技能没有深层引用链。

- [页面结构与层级](references/structure-hierarchy.md)：必需章节顺序、章节摘要、从用户到开发者的推进、Docs 树放置、小规则文件、Further Exploration 与 Dev Note 归属。
- [页面风格](references/style.md)：简短摘要、受控技术表达、`-----` 章节分隔线、可折叠内容节与强调纪律。
- [评审标准](references/review.md)：新人测试、证据检查与校验命令。

句子级契约覆盖与编辑判断用 [wdp-prose-standard](../wdp-prose-standard/SKILL.md)。

<a id="validation"></a>

## 校验

校验受影响的格式，而不只是 Markdown 语法。强承诺需要一份聚焦的有效 fixture，以及一份证明顶层门禁会变红的无效 fixture。

- 散文格式：`verify-md-wrap` 拒绝硬折行段落，`verify-md-links` 检查相对链接与锚点，`verify-doc-budgets` 执行词数上限。
- 教程：走通文档所写的入口路径，或点明一个明确的人工验证所有者。
- 技能：运行仓库的技能调用元数据检查。

先用 `npm run test:docs` 跑快速综合文档检查（换行、链接、预算、Agent Note 门禁、技能元数据），改动门禁脚本时再跑 `npm run verify-all`。
